# Less3 Performance and Scalability Improvements

## Ranking Method

Items are stack-ranked first by expected production impact, then by implementation complexity. Impact and complexity use `High`, `Medium`, and `Low`; when impact is equal, lower-complexity work is listed earlier unless a dependency forces a different order.

## Implementation Notes

- Rank 1 first pass is implemented for request-history list/report/cleanup flows: REST enumeration, admin request summaries, admin request reports, and maintenance purge counts now use bounded `EnumerationQuery`/`EnumerationResult<T>` database reads instead of broad in-memory request-history scans. Full SQL-side aggregate endpoints remain a later optimization under rank 10.
- Rank 3 is implemented for the REST collection surface: users, credentials, buckets, objects, tags, ACLs, uploads, and request history now use database-backed enumeration helpers with whitelisted sort fields and total counts.
- Rank 9 is implemented with `Padlocks.Padlock<string>` for keyed single-flight bucket creation/removal and a concurrent keyed bucket-client registry.
- Rank 14 is explicitly deferred for now because storage layout changes are disruptive without production evidence that directory cardinality is the bottleneck.
- Rank 15 connection lifecycle audit is complete for the current provider execution/migration paths; the hot paths reviewed use scoped connection/command lifetimes. Parameterization, command timeout policy, and pool tuning remain future work after more load data is available.
- Rank 18 is implemented as a regression guardrail: shared live-server performance tests are exposed through `Test.Automated`, `Test.Xunit`, and `Test.Nunit`, and `Test.PerformanceBenchmark` provides an operator-run benchmark harness.

| 2 | Database | Add query-plan checks and covering indexes for hot paths across all providers. | High | Low-Medium | Existing setup scripts include many indexes, but several hot reads combine `tenant_id`, bucket/object/resource identifiers, key, version, delete marker, dates, and active flags. | 3 | REST API | Make all collection endpoints DB-native for filter/sort/page operations. | High | Medium | `RestApiHandler` builds pages with `BuildResult(_Config.GetUsers/GetCredentials/GetBuckets/GetObjects/...)`, which materializes full lists before `Skip/Take`. | 4 | S3 API | Ensure S3 list operations are fully query-backed with stable continuation semantics. | High | Medium | Object enumeration APIs support bucket/prefix/paging, but S3 list handlers should not materialize object sets for delimiter, continuation, or filtering logic at scale. | Implement S3 `ListObjectsV1/V2` as provider queries using `(tenant_id, bucket_id, key)` ordering, prefix/range predicates, max-keys + 1 reads, stable continuation tokens, delimiter/common-prefix derivation, and no full-bucket scans. |
| 5 | Authentication/RBAC | Cache credential lookup and effective authorization decisions with explicit invalidation. | High | Medium | `AuthManager` resolves credentials by access key on requests and `TryAuthorizeRbac` enumerates role assignments and permissions for authorization checks. | Add bounded caches keyed by access key and by `(tenant_id, principal_type, principal_id, resource_type, resource_id, operation)`. Invalidate on credential/user/tenant/role/permission/assignment mutation and use short TTLs as a fallback. Keep deny decisions cacheable only when tied to the current RBAC version. |
| 6 | Request/audit logging | Move request-history and authorization-audit writes off the request path. | High | Medium | Request history insert methods are synchronous wrappers around database writes; rows include request/response body fields, which can be wide and slow. | Use a bounded `Channel<T>` with background batched writers, drop/degrade policy for overload, metrics for dropped entries, and separate lightweight list columns from optional body capture. Batch inserts per provider. |
| 7 | S3 API/storage | Stream object uploads, downloads, and ranges end to end without whole-object buffering. | High | Medium-High | `ObjectHandler` reads `ctx.Request.DataAsBytes` in write paths. `DiskStorageDriver` uses `File.ReadAllBytes`, byte-array async reads, and `MemoryStream` buffering for range streams. | Add stream-first storage APIs and response writers. | 8 | Database/API internals | Convert database interfaces and callers to async end to end. | High | High | Many provider implementations block async calls via `.Result`, `.Wait()`, and `GetAwaiter().GetResult()` from `ConfigManager` and database method wrappers. | Introduce async interfaces alongside current sync methods, migrate hot request paths first, then remove sync wrappers. | 9 | Bucket registry | Replace the locked bucket-client list with keyed concurrent lookup and single-flight creation. | Medium | Low-Medium | `BucketManager` stores bucket clients in a `List<BucketClient>` under `_BucketsLock` and uses `Exists`/`First` scans for lookups. | Use the Padlock NuGet package (`Padlocks.Padlock<T>`) for keyed single-flight creation/update/delete around `(tenant_id, bucket_name)` while storing clients in a concurrent keyed registry. | 10 | Admin/dashboard REST | Replace fixed-limit scans with aggregate endpoints for dashboard stats and maintenance views. | Medium | Low-Medium | Admin handlers enumerate buckets and then call object lists with fixed limits for stats. Avoid using list endpoints as report sources. |
| 11 | API protection | Add server-side cost controls for expensive routes and multipart operations. | Medium | Low | Listing, reporting, multipart completion, maintenance cleanup, and export routes can be expensive under high cardinality. | Enforce max page sizes, max date ranges, max prefix fanout, request body size limits, multipart part limits, and tenant-scoped concurrency limits. Return clear validation errors before starting expensive work. |
| 12 | Serialization | Reduce REST serialization overhead for high-volume responses. | Medium | Medium | REST responses are object-list heavy, and performance will become serialization-bound after database paging is fixed. | Use source-generated `System.Text.Json` contexts for DTOs, stream large JSON arrays when practical, avoid reflection-heavy serialization on hot paths, and avoid serializing body/blob columns in list DTOs. |
| 13 | Multipart uploads | Optimize multipart part lookup, completion, and cleanup. | Medium | Medium | Upload and part methods read parts by upload ID and delete by upload/part; completion can become database and filesystem intensive with many parts. | Add unique `(tenant_id, upload_id, part_number)` constraints, ordered part queries, checksum metadata, batched part delete, resumable cleanup, and provider transactions around complete/abort metadata changes. |
| 14 | Storage layout | Deferred: shard on-disk object paths and cleanup work to avoid large directories and long blocking deletes. | Medium | High | Disk storage maps object keys to files and bucket deletion recursively clears directories. Large buckets can create expensive directory scans and long delete pauses, but changing the object layout is disruptive. | Do not start this as an early optimization. For now, measure directory cardinality and delete latency, document operational thresholds, and only revisit sharding/tombstones when evidence shows the current layout is a production bottleneck. |
| 15 | Database providers | Audit connection lifecycle, then tune provider-specific pooling, prepared commands, and parameterized execution. | Medium | Medium-High | Query helpers build SQL strings and execute through provider wrappers; hot paths can benefit from parameterized commands, plan reuse, and explicit pooling settings. | 16 | Config/control plane | Use immutable read snapshots for settings and small reference data. | Low-Medium | Low | Maintenance settings can be updated at runtime, and auth/control-plane paths repeatedly read related reference data. | Publish immutable snapshots for settings and small lookup tables with version numbers. | 17 | Conditional responses | Expand conditional request handling and metadata short-circuiting. | Low-Medium | Medium | S3 and REST metadata routes can avoid body work when validators match. | Ensure `If-None-Match`, `If-Match`, `If-Modified-Since`, range validation, and HEAD paths avoid opening object streams unless required. | 18 | Performance testing | Add repeatable throughput/latency regression tests for hot S3, REST, and internal paths. | Medium | Low-Medium | Existing tests validate behavior and security, but they do not gate large-list, large-object, high-concurrency, or report-query regressions. | Add a benchmark/integration suite that seeds large tenants, buckets, objects, RBAC assignments, request history, and multipart uploads against a temporary Less3 instance. Track S3 PUT/GET/LIST, REST list/report, auth checks, and cleanup latencies. |

## Recommended First Milestone

1. Implement database-native request-history/report queries and REST collection paging for the routes that power the dashboard, using `EnumerationQuery`/`EnumerationResult<T>` for list flows.
2. Add query-plan/index coverage tests for SQLite first, then mirror the assertions for PostgreSQL, MySQL, and SQL Server.
3. Add credential/RBAC caching with invalidation hooks around the existing mutation paths.
4. Convert S3 object write/read paths to stream-first APIs for uploads, downloads, and ranges.
5. Start the performance regression harness once the first three changes land, so subsequent work has measurable guardrails.
6. Before any database pool-size or prepared-command tuning, complete the connection lifecycle audit and remediate leak risks across all supported providers.
